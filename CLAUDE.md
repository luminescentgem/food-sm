# CLAUDE.md

@AGENTS.md

`AGENTS.md` holds generic Symfony conventions. This file holds the project-specific
decisions. **Where the two conflict, this file wins.**

## Project: Food SM

A food app built around collecting each user's food tastes. Long-term it has four
parts: taste collection, a social layer (compare tastes with friends), meal planning,
and a dinner/event organizer that suggests recipes everyone at the table will like.
The full taste model and the post-MVP plans (tier 3 orderings, score projections,
recipes) live in the project ROADMAP, not here.

Core data model: users judge **variants** (an ingredient in a given preparation:
raw tomato, grilled zucchini). A judgment is either a **swipe** (liked / disliked
verdict, never mapped to a number) or a **rating** (integer 0–10). Judgments are
**append-only events**; only the latest swipe and the latest rating per
(user, variant) count. All data is public for now.

## MVP scope

Goal: prove that the swipe interface works and that the taste data is useful.
Keep it minimal but complete.

### Data

All ids are UUIDs (v7, generated by the application, stored as GUID columns).

| Table | Module | Notes |
|---|---|---|
| `users` | Identity | id, name, created_at. 3 hardcoded users with fixed ids (`UserFixtures`), no auth |
| `preparations` | TasteCollection | id, name (unique), parent_id: a tree (raw / cooked → grilled, steamed…) |
| `ingredients` | TasteCollection | id, name (unique), category, region, commonness (0–1), default_preparation_id, created_at |
| `ingredient_variants` | TasteCollection | id, ingredient_id, preparation_id, unique (ingredient_id, preparation_id). The MVP seeds only each ingredient's default variant |
| `taste_judgments` | TasteCollection | id, user_id, variant_id, liked (nullable), score (nullable, 0–10), created_at. Exactly one of liked / score is set (enforced by the `TasteJudgment` entity, not the DB). No FK on `user_id` (Identity's table) nor on `variant_id` (existence is checked in the handlers) |

Seed data: `src/TasteCollection/Infrastructure/Fixtures/data/ingredients.json`
(283 French ingredients, 17 preparations; category and region vocabularies are
listed at the top of the file), loaded through the domain constructors.

### API (JSON, all under `/api`)

Built:

```
POST /api/users/{userId}/swipes    body: { "variantId": uuid, "liked": bool }      → 201, the recorded judgment
POST /api/users/{userId}/ratings   body: { "variantId": uuid, "score": 0-10 }      → 201, the recorded judgment
GET  /api/users/{userId}/top?limit=5   (limit 1–50)                                 → 200, { userId, ratedVariants: [...] }
```

Errors: unknown variant → 404, invalid body or query → 422.
Known gap: an unknown `userId` is not detected yet (needs `Identity/Api`, see below).

To build, in this order:

```
GET  /api/users/{userId}/cards?limit=20   → next variants to judge (MVP: unjudged default variants, most common first)
GET  /api/ingredients?q=…                 → search by ingredient name
     comparison of two users (verdict + score per variant)
```

### Frontend (separate, React + TypeScript)

Swipe page (swipe + rate on the card), profile (top 5), search by name, two-user
side-by-side comparison. Readable and mobile-friendly; no styling work beyond that.

### Out of scope for the MVP

Do not build these, even partially: authentication, friending or privacy controls,
region filtering (the `region` field exists but isn't used), recipes, meal planning,
event organization, card selection beyond simple ordering, tier 3 orderings and
fitted scores, the `current_scores` projection.

### Open questions (ask, don't decide)

- Whether the two-user comparison lives in Social (calling `TasteCollection/Api`)
  or in TasteCollection. The principle below says comparison is Social's job.

## Architecture: modular monolith

One Symfony app, structured so a module could later become a separate service without
a rewrite. Not microservices: one process, one database.

### Modules

| Module | Owns | Status |
|---|---|---|
| `Identity` | Users (names and profile info) | MVP |
| `TasteCollection` | Ingredients, preparations, variants, taste judgments | MVP |
| `Social` | Viewing and comparing users' profiles and scores | MVP (not started) |
| `MealPlanning`, `EventHelper` | – | Don't create until work on them actually starts |
| `Shared` | Generic value objects (`Id`, `UserId`), the `IdGenerator` port and its framework-backed implementations | – |

Other modules refer to users only by `Shared\Domain\Model\UserId`. Anything more
(names, profile info, existence checks) comes from `Identity/Api`.

### Layout and layers

```
src/<Module>/
  Api/             the module's published contract: API interface, its DTOs and public events.
                   The ONLY part of a module other modules may import.
  Domain/
    Model/         entities and value objects (ids), plain PHP
    Repository/    write-side ports (one per stored entity)
    Specification/ named descriptions of read needs (e.g. CurrentRatings, TopRated)
    Exception/     domain exceptions, one abstract base per module
    Event/         internal domain events
  Application/
    UseCase/       commands / queries + their handlers (one handler per use case)
    Reader/        read-side ports: take Domain specifications, return Application DTOs
    Dto/           response DTOs, one per screen / use case, primitives only
  Infrastructure/
    Http/          Controller/ (one invokable controller per endpoint), Request/ (request DTOs + Assert)
    Persistence/   Doctrine/ (repositories, XML mapping, id types), Dbal/ (readers, plain SQL)
    Fixtures/      fixtures and Foundry factories
src/Shared/
  Domain/          Model/ (Id, UserId), Service/ (IdGenerator port)
  Infrastructure/  UUID v7 generator, Doctrine IdType base
src/DevFixtures/   dev data spanning several modules (outside deptrac layers)
```

Namespaces: `App\<Module>\<Layer>\...` (the single `App\` → `src/` PSR-4 root).
File path, namespace and class name must match.

### Rules

1. **Each module is a vertical slice**: its own domain logic, data access and HTTP
   endpoints. Don't split by technical concern across modules.
2. **Dependencies point inward**: Domain → Shared.Domain only. Application → its own
   Domain and Api, Shared.Domain. Infrastructure → its own Application, Domain and Api,
   Shared, Symfony and Doctrine. **Domain, Application and Api never import `Symfony\`
   or `Doctrine\`.** Api depends on Shared.Domain only, so no internal type leaks
   through the contract.
3. **Cross-module imports target only `<Module>/Api`**, and only from another
   module's Application or Infrastructure, never from its Domain. Never touch another
   module's Domain, Application or Infrastructure.
4. **Each module owns its tables.** No module queries another module's tables, and
   there are no foreign keys across modules, even though they share one database.
5. **No shared domain model.** When a module needs a concept it doesn't own, it
   defines its own minimal read model of it and gets the data through the owner's Api.
6. **Blocking calls that need a return value** go through the Api interface.
   **Side effects that don't block the caller** (cache invalidation, stats,
   notifications) go through events published in `<Module>/Api` (Symfony's
   in-process event dispatcher). Put a dispatcher interface in Application and
   implement it in Infrastructure.
7. **Design APIs to be coarse**: batch-friendly methods (e.g. scores for many
   variants at once), not chatty per-item calls, so they still make sense if a
   module ever sits behind a network.

`deptrac.yaml` enforces rules 2 and 3. **Run `composer deptrac` after every change
that adds a `use` statement across layers or modules; a violation is a bug, not
something to whitelist.** Changing `deptrac.yaml` itself needs explicit approval.
Known limitation: deptrac allows every module to import every other module's Api,
so it does not catch dependency cycles between modules.

### Writes: use cases and entities

- A use case = a command object (verb-named, `final readonly`, e.g. `RateVariant`)
  + one handler (`RateVariantHandler`, `__invoke`). Handlers check what the domain
  needs (e.g. the variant exists, via `IngredientVariantRepository::exists()`),
  build entities through their named constructors, call the repository, and return
  a response DTO built from the entity (`XxxDto::fromJudgment()`).
- Entities have private constructors and named constructors that enforce their
  invariants (`TasteJudgment::swipe()` / `::rating()`), and expose state through
  `public readonly` properties. No setters.
- Ids come from the `IdGenerator` port; time comes from `Psr\Clock\ClockInterface`.
  Never call `new \DateTimeImmutable()` or generate UUIDs inside a handler or entity.
- Never use `assert()` for validation: it is compiled out in production.

### Reads: specifications and readers

- Reads don't go through repositories and don't load entities.
- A Domain **specification** names a read rule (`CurrentRatings` = the latest rating
  per variant counts; `TopRated` = the best N of those). It is a plain description:
  no SQL, no behaviour.
- An Application **reader** port takes specifications and returns **one DTO per
  screen** (`RatingsReader::topRated(TopRated): list<CurrentlyRatedDto>`). Methods
  are named after the need, not a generic `matching()`.
- The Infrastructure implementation (DBAL, plain SQL) writes each rule's SQL
  **once**, as a private fragment method, and composes fragments as subqueries.
  "Latest per (user, variant)" uses `ROW_NUMBER() OVER (PARTITION BY …)`.
  Row → DTO mapping happens in the reader, not in the DTO.
- The handler assembles the screen's DTO (e.g. wraps the list with the user id).
- Selection and aggregation rules go in SQL fragments; calculation and decision
  rules (roll-ups, vetoes, thresholds, fitted scores) go in Domain PHP, unit-tested.

### Persistence

- Doctrine ORM with **XML mapping**, stored in
  `src/<Module>/Infrastructure/Persistence/Doctrine/Mapping/<ShortClassName>.orm.xml`.
  Domain entities have **no ORM attributes**. This overrides AGENTS.md's
  "prefer attributes" for entity mapping.
- **Don't use `make:entity`**: it generates attribute-mapped entities in `src/Entity`.
  Hand-write the domain class and its XML mapping, and add a new module's mapping
  block to `config/packages/doctrine.yaml`.
- Every id value object has a Doctrine type (extend `Shared\Infrastructure\Persistence\Doctrine\IdType`),
  registered under `doctrine.dbal.types`.
- Name indexes and unique constraints explicitly in the XML (`<indexes>`,
  `<unique-constraints>`), not with `unique="true"`, so names match the migrations
  and `doctrine:schema:validate` passes.
- Repository interfaces live in `Domain/Repository/`. Doctrine implementations live in
  `Infrastructure/Persistence/Doctrine/`. Readers live in `Infrastructure/Persistence/Dbal/`.
- Migrations: one folder (`migrations/`), but each migration touches **one module's
  tables only** and its description starts with the module name, e.g.
  `[TasteCollection] create ingredients table`. Either generate with `make:migration`
  and split by module, or hand-write them with DBAL's editor API
  (`Table::editor()` …, then `$this->platform->getCreateTablesSQL()` + `addSql()`):
  the mutable Schema API (`$schema->createTable()`, `addColumn()`…) is deprecated
  since DBAL 4.5. After migrating, `doctrine:schema:validate` must pass.
- Validation (`#[Assert\...]`) goes on request DTOs in Infrastructure/Http, not on
  domain entities. The domain enforces its own invariants in plain PHP (e.g.
  `TasteJudgment::rating()` throws `InvalidScore` outside 0–10). API-only limits
  (e.g. `limit` ≤ 50) stay in the HTTP layer.

### Errors

- Domain exceptions extend their module's abstract base (`TasteCollectionException`,
  itself a `\DomainException`) and never mention HTTP.
- Map them to status codes centrally under `framework.exceptions` in
  `config/packages/framework.yaml` (specific classes before base classes). Don't
  catch domain exceptions in controllers.

### Wiring

- Every class in `src/` is autowired, except `*/Domain/Model/`, `*/Domain/Event/`
  and `*/Domain/Specification/`. Ports (`Domain/Repository/`, `Application/Reader/`,
  `Shared/Domain/Service/`) must stay scanned so their single implementation is
  aliased automatically.
- Add an explicit alias (`#[AsAlias]`) only when a second implementation appears.
- Controllers are plain classes with `#[AsController]` (they don't extend
  `AbstractController`; this overrides AGENTS.md). Path parameters that are ids get
  `requirements: ['…' => Requirement::UUID]`. Request bodies use
  `#[MapRequestPayload]`, query parameters `#[MapQueryParameter]` /
  `#[MapQueryString]`. Responses are serialized with `SerializerInterface`
  (`JsonResponse::fromJsonString()`).
- Routes: each module's `Infrastructure/Http/Controller/` is loaded in
  `config/routes.yaml` with the `/api` prefix, and routes are declared with `#[Route]`.
  A new module needs its own entry there.

## Stack and environment

- PHP ≥ 8.4, Symfony 8.x, Doctrine ORM 3 / DBAL 4, SQLite, Foundry for factories.
- The SQLite file is `var/data_<env>.db` (from `DATABASE_URL` in `.env`); override it
  in `.env.local` if needed. SQLite needs no `doctrine:database:create`; the file is
  created on first connection.
- Dev data: `php bin/console doctrine:fixtures:load -n` (users, the ingredient seed,
  and a random taste history from `src/DevFixtures/`).
- Answers to AGENTS.md's "ask before generating" questions:
  persistence is Doctrine ORM (XML mapping) for writes and DBAL for reads; the
  interface is a JSON API only (no Twig); there is no auth in the MVP.

## Commit messages

[Conventional Commits 1.0](https://www.conventionalcommits.org):

```
<type>(<scope>)<!>: <description>

<body>

<footers>
```

### Type

| Type | Use for |
|---|---|
| `feat` | New or changed behaviour a caller can see: endpoint, use case, field, UI screen |
| `fix` | A bug fix |
| `perf` | A performance improvement with identical behaviour |
| `refactor` | Any other code change with identical behaviour |
| `style` | Formatting only (php-cs-fixer, Prettier), no code change |
| `test` | Tests added or changed on their own |
| `docs` | Documentation only: `CLAUDE.md`, `AGENTS.md`, READMEs, comments |
| `build` | Dependencies and build setup: `composer`/`npm` changes (with the recipe files they generate), Vite/TypeScript config |
| `ci` | CI pipelines |
| `chore` | Everything else that isn't shipped code: dev tooling config (deptrac, PHPStan, php-cs-fixer, editorconfig), scaffolding, fixtures and seed data |
| `revert` | Reverting an earlier commit (see below) |

When two types fit, take the first one in this table. A change is one type: a
`feat` commit includes its tests, its migration and XML mapping, and any
`CLAUDE.md` update that describes it. `test` and `docs` are only for commits that
contain nothing else.

### Scope

The part of the repository the change lives in, spelled as its directory:

- a backend module: `Identity`, `TasteCollection`, `Social`, `Shared`
  (`src/<Module>/`, and that module's migrations, config blocks and tests);
- `frontend` for the React app (`frontend/`).

Leave the scope out when a change spans several of these or touches none of them
(root config, `deptrac.yaml` as a whole, `CLAUDE.md` sections that aren't about one
module).

A feature that needs both an endpoint and a screen is **two commits**: the backend
one first, then the `frontend` one. Each migration touches one module's tables, so a
commit never adds migrations for two modules.

### Description

- Imperative mood (`add`, not `added`/`adds`), no final period.
- Starts with a lowercase letter; identifiers keep their casing
  (`batch score lookups through TasteCollectionApi`).
- The whole header, type and scope included, fits in 72 characters.
- Says what changes for someone reading the log, not which files moved.

### Body and footers

- The body is optional. Write one when the *why* isn't obvious from the diff:
  a decision, a rejected alternative, a constraint. Wrap at 72 characters.
- Footers use git trailer syntax (`Token: value`), one per line, after a blank
  line. `Co-Authored-By:` goes here.
- **Claude attribution**: add the `Co-Authored-By: Claude` footer only when Claude
  produced code in the commit. Leave it out when Claude only wrote the commit message.
- **Breaking changes**: add `!` before the colon **and** a `BREAKING CHANGE:`
  footer explaining the change and what callers must do. This is required whenever
  an `/api` contract changes (path, method, request body, response shape, status
  codes), because the frontend depends on it. The frontend commit that adapts to it
  follows right after.
- **Reverts**: `revert: <header of the reverted commit>`, with the body
  `This reverts commit <sha>.` and a line on why.

### Granularity

- **One logical change per commit.** If the description needs "and" to join two
  unrelated things, split it.
- Every commit leaves the repo working: `lint:container`, `composer deptrac` and
  `php bin/phpunit` pass (and the frontend builds, once it exists).
- Don't add version or maintenance-type tags (`[minor]`, `[évolutive]`, …).
  Versioning, if ever needed, is derived from the types and `!`.

### Examples

```
feat(TasteCollection): add score upsert endpoint
feat(frontend): add swipe page
fix(Identity): return 404 for unknown user id
perf(TasteCollection): load top ingredients in a single query
refactor(Social): batch score lookups through TasteCollectionApi
style: apply php-cs-fixer @Symfony ruleset
build: add symfony/lock
build(frontend): upgrade vite to 7
chore: allow Social to depend on Identity in deptrac
chore(TasteCollection): add ingredients CSV fixture
docs: record ingredient source decision
```

```
feat(TasteCollection)!: return top ingredients as objects

The profile page needs names alongside scores; returning ids forced
one extra request per ingredient.

BREAKING CHANGE: GET /api/users/{userId}/ingredients now returns
[{ id, name, score }] instead of a list of ids.
```
